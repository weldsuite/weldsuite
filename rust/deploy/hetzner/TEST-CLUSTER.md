# The EU test cluster

A test cluster on Hetzner, built with the runbook ([README.md](README.md)) but
following `develop` instead of release tags, so the Rust port runs on real
servers before the EU edition launches, and stays in step with Global: every
develop push that the "Rust images" workflow builds reaches this cluster, as
every develop push reaches Global's test environment. Its names
(`weldsuite-eu-test`, `test.weldsuite.eu`, the `test` Flux cluster) keep it
apart from the future production cluster (`eu`).

How a develop push gets here: the workflow builds the images
(`ghcr.io/weldsuite/weldsuite`, `-sign-portal`, `-collab-rooms`, tagged
`sha-<commit>`) and publishes the chart of the same commit as
`oci://ghcr.io/weldsuite/charts/weldsuite`, version `<chart>-develop.<run>`,
with that tag as its appVersion. Flux checks for a newer chart every five
minutes (`clusters/test/weldsuite-develop.yaml`) and upgrades the release; the
migration Job runs first. The rest of the configuration (layers, values,
secrets) comes from `develop` itself. There is no deploy branch to merge into
and no tag to bump. (Until November 2026 the cluster followed a
`deploy/eu-test` branch; "Switching to develop" below moves a cluster built
that way.)

The marketing site runs here too, at `www.test.weldsuite.eu` (English) and
`nl.test.weldsuite.eu` (Dutch), and follows the `main` branch of the private
`weldsuite/weldsuite-eu-marketing` repository the same way: its "EU test
image" workflow builds `ghcr.io/weldsuite/weldsuite-marketing:test-sha-<commit>`
with those two URLs compiled in and publishes its chart as
`oci://ghcr.io/weldsuite/charts/weldsuite-marketing`, version
`<chart>-main.<run>`; the `marketing` layer (`flux/apps/marketing`) takes the
newest.

Size: **six CX23** (2 vCPU / 4 GB each) in nbg1, one control plane and five
workers, plus the two load balancers (still in fsn1, where the cluster started
on one CPX32; see "Moving the cluster"), so the paths match production. About
€50 a month, a fraction of the launch topology (3 control-plane nodes, 3
workers, 2 dedicated Postgres nodes), billed by the hour; `tofu destroy` stops
it. For customers, drop `test.tfvars.example`'s size lines (the defaults are
the launch topology) and use the `eu` Flux cluster.

## What differs from the runbook

| | Runbook (`eu`) | This cluster (`test`) |
|---|---|---|
| Servers | 3 control plane, 3 workers, 2 Postgres | 1 control plane, 5 workers, all CX23 (`test.tfvars.example`) |
| Postgres | 2 instances each, synchronous replica, own pool | 1 instance each, small (`infrastructure/configs/test`) |
| Other replicas | 2 or more; NATS a three-node cluster | 1 each; one NATS server (patches in `clusters/test/layers.yaml`) |
| Flux path | `clusters/eu` | `clusters/test` |
| Git source | `--branch=main`, chart from a release tag | `--branch=develop`; the chart is the newest develop build's (`clusters/test/weldsuite-develop.yaml`) |
| Secrets | `secrets/eu` | `secrets/test`, generated by `flux/scripts/fill-secrets.mjs` |
| Images | the EU registry, later | `ghcr.io/weldsuite/*:sha-<commit>`, pushed by the "Rust images" workflow for every develop build; the chart names them (`WELDSUITE_IMAGE_TAG` is empty) |
| Backups | a second EU provider | Hetzner Object Storage in nbg1, which since the move is the nodes' own location |
| OpenTofu state | S3 backend, encrypted | local `terraform.tfstate` in this checkout |
| Metrics | metrics-server (the autoscaler's) | metrics-server, plus a small Prometheus for Lens (`infrastructure/monitoring`) |
| Marketing site | not yet (it needs a build with production's URLs) | `www.` and `nl.test.weldsuite.eu`, the newest `weldsuite-eu-marketing` main build (`flux/apps/marketing`) |

**The state is local:** it holds the Talos secrets and is the only easy way to
tear the cluster down. Don't delete this checkout while the cluster exists (if
it's lost, delete the servers, load balancers, network, firewall and placement
groups labelled `cluster=weldsuite-eu-test` in the Hetzner console).

## Steps

Run everything from this checkout (Git Bash), on `develop` or a branch off it.
Changes to the cluster's configuration go to `develop` through a pull request,
like any other change.

1. **Tools.** Next to the `tofu`, `kubectl` and `helm` you have:

   ```bash
   winget install Sidero.talosctl FluxCD.Flux SecretsOPerationS.SOPS FiloSottile.age
   ```

   and `hcloud-upload-image` (a release binary from
   github.com/apricote/hcloud-upload-image, or
   `go install github.com/apricote/hcloud-upload-image@latest`).

2. **Hetzner.** A Cloud project and a read/write API token:
   `export TF_VAR_hcloud_token=… HCLOUD_TOKEN=…` (never in a file).

3. **Object storage**, in the same project: buckets
   `weldsuite-eu-test-files` (fsn1) and `weldsuite-eu-test-pg-backups` (nbg1),
   and S3 credentials. If a name is taken, pick another and change it in
   `rust/deploy/flux/clusters/test/cluster-settings.yaml`.

4. **The Talos image:**
   `TALOS_VERSION=v1.14.3 rust/deploy/hetzner/scripts/upload-talos-image.sh`

5. **Servers.** `cp test.tfvars.example terraform.tfvars` in
   `rust/deploy/hetzner` (git-ignored) and put your address in `admin_cidrs`.
   CX23s are often sold out: `GET /v1/server_types?name=cx23` lists the
   locations where one is `available`; use one of them in both location
   lists. Then:

   ```bash
   cd rust/deploy/hetzner
   tofu init
   tofu apply
   tofu output -raw kubeconfig  > kubeconfig  && export KUBECONFIG=$PWD/kubeconfig
   tofu output -raw talosconfig > talosconfig && export TALOSCONFIG=$PWD/talosconfig
   kubectl get nodes -L topology.kubernetes.io/zone,node.weldsuite.org/pool
   ```

6. **DNS.** The records `tofu output dns_records` prints (`app.`, `api.`,
   `auth.`, `sign.`, `livekit.`, `turn.` under `test.weldsuite.eu`, A and AAAA
   to the ingress load balancer) go in the `weldsuite.eu` zone in Hetzner DNS,
   in the same project: the Cloud API's `/zones/weldsuite.eu/rrsets`, with the
   same token. Add `www.` and `nl.` (the marketing site) to the same load
   balancer; the output leaves them out because production doesn't run the
   site yet.

7. **Secrets.**

   ```bash
   cd rust/deploy/flux
   age-keygen -o ~/weldsuite-eu-test.agekey   # outside git; the private key into the password manager
   # put the "public key" line in .sops.yaml, rule secrets/test
   FILES_S3_ACCESS_KEY_ID=… FILES_S3_SECRET_ACCESS_KEY=… \
   BACKUP_S3_ACCESS_KEY_ID=… BACKUP_S3_SECRET_ACCESS_KEY=… \
     node scripts/fill-secrets.mjs secrets/test/secrets.sops.yaml
   # delete the `registry` Secret from it once the images are public (step 8),
   # or set GHCR_USER/GHCR_TOKEN (a classic token with read:packages);
   # MARKETING_GHCR_USER/MARKETING_GHCR_TOKEN fill marketing/ghcr ("The marketing site")
   sops --encrypt --in-place secrets/test/secrets.sops.yaml
   # uncomment secrets.sops.yaml in secrets/test/kustomization.yaml
   ```

   Check `git diff` shows only `ENC[…]` values before committing.

8. **Images and chart.** Nothing to set: the newest develop build's chart
   names its images. The first develop build creates the packages
   `weldsuite`, `weldsuite-sign-portal`, `weldsuite-collab-rooms` and
   `charts/weldsuite` as private: make all four public in their package
   settings on GitHub (the repository is public). Otherwise keep the
   `registry` Secret from step 7 for the images, and give
   `clusters/test/weldsuite-develop.yaml` a `secretRef` to a docker-registry
   Secret in `flux-system` for the chart. The marketing site's packages
   (`weldsuite-marketing`, `charts/weldsuite-marketing`) stay private, like
   `weldsuite-eu-marketing`; the cluster reads them with a token ("The
   marketing site").

9. **Commit** the settings and the encrypted secrets and get them into
   `develop` (a pull request).

10. **Flux** (runbook step 6, with `develop` and this path). The flux CLI must
    be the version it installs (v2.9.6; a newer CLI refuses). The repository
    is public and the organisation doesn't allow deploy keys, so Flux reads it
    over anonymous HTTPS, with no key:

    ```bash
    flux install --version=v2.9.6
    kubectl -n flux-system create secret generic sops-age --from-file=age.agekey=$HOME/weldsuite-eu-test.agekey
    flux create source git flux-system \
      --url=https://github.com/weldsuite/weldsuite --branch=develop
    flux create kustomization flux-system \
      --source=GitRepository/flux-system --path=./rust/deploy/flux/clusters/test --prune=true
    flux get kustomizations --watch
    ```

    The `video` layer (LiveKit) waits for the `livekit.` and `turn.` records
    from step 6 and their certificates. OpenTofu labels two workers for it
    and opens their media ports (runbook, "Video").

11. **Zitadel** (runbook step 7): first admin, the `WeldSuite` project, the
    `platform` application. Put the project id and client id in
    `cluster-settings.yaml`, push; Flux rolls the server.

12. **Look:** `https://auth.test.weldsuite.eu/ui/console`,
    `https://api.test.weldsuite.eu/health` and `/config.json`,
    `https://app.test.weldsuite.eu`,
    `kubectl -n weldsuite logs deploy/weldsuite`, and the marketing site at
    `https://www.test.weldsuite.eu` and `https://nl.test.weldsuite.eu`.

## The marketing site

`flux/apps/marketing`: a HelmRelease of the site's chart in the `marketing`
namespace, one pod, behind Traefik with a Let's Encrypt certificate for both
hosts. It shares nothing with the platform.

Its chart and image stay private, like `weldsuite-eu-marketing`. The layer
reads the chart through its own source (`source.yaml`) and the pods pull the
image with the same Secret, `marketing/ghcr`: a classic GitHub token with only
`read:packages`, of an account that can read that repository (a machine
account's, preferably, so it outlives anyone leaving). Put it in with the age
key (step 7):

```bash
MARKETING_GHCR_USER=<account> MARKETING_GHCR_TOKEN=<token> SOPS_AGE_KEY_FILE=~/weldsuite-eu-test.agekey \
  node rust/deploy/flux/scripts/fill-secrets.mjs --update rust/deploy/flux/secrets/test/secrets.sops.yaml
```

When the token expires or is revoked, Flux reports a 401 on the chart and
new pods can't pull the image (running ones keep running): replace it the
same way, after deleting the old `.dockerconfigjson` in `sops
secrets/test/secrets.sops.yaml`. Two things work differently from Global:

- **Prices** are the site's fallback prices (`lib/pricing.ts` there): the site
  reads plans over Neon's HTTP driver, which the cluster's Postgres doesn't
  speak, so it gets no `MASTER_DATABASE_URL`.
- **The contact and support forms** are not delivered: no `RESEND_API_KEY`.
  Either goes in a Secret named by `existingSecret` in
  `flux/apps/marketing/values/marketing.yaml`.

The site is built with noindex and without analytics. To add it to a cluster
built before it: the `www.` and `nl.` records (step 6), a first run of the
"EU test image" workflow in `weldsuite-eu-marketing` (a push to its `main`, or
Run workflow) and the token above, then this change in `develop`.
`flux get helmreleases -n marketing` shows the build it runs.

## Metrics in Lens

The cluster's **Settings → Metrics**: Prometheus **Prometheus Operator**,
service address `monitoring/kube-prometheus-stack-prometheus:9090`. The usage
columns come from metrics-server (`kubectl top nodes` shows the same).

Both verify the kubelets' certificates, which the cluster CA signs
(`serverTLSBootstrap` in `talos/common.yaml.tftpl`, approved by
`kubelet-serving-cert-approver` in the controllers layer). A node created
before that setting needs it once, without a reboot:

```bash
printf 'apiVersion: v1alpha1\nkind: KubeletConfig\nconfig:\n  serverTLSBootstrap: true\n' > kubelet.yaml
talosctl -n <private ip> patch machineconfig --patch @kubelet.yaml
kubectl get csr   # kubelet-serving, Approved,Issued
```

## Moving the cluster

On 2026-10-31 the cluster moved from one CPX32 in fsn1 to six CX23s in nbg1,
keeping its data and Zitadel. The cheap types sell out within minutes, so the
servers were bought in the console when they were free and adopted, not
created by OpenTofu:

1. **Each new server:** the cluster's firewall first (a Talos node without a
   config accepts one from anyone on port 50000), then, powered off, the
   placement group of its location, the name and labels `servers.tf` gives
   it, and the network with its fixed address (workers from 10.10.1.20). Then
   a rebuild from the Talos snapshot with its machine config as user data
   (`POST /servers/{id}/actions/rebuild` takes `user_data`). The configs come
   from `tofu show -json` of a plan made with the new tfvars
   (`data.talos_machine_configuration.node` in `prior_state`). Workers join
   the running cluster straight away.
2. **Adopt them** with `import {}` blocks (`tofu import` fails: the `nodes`
   output indexes every node), then plan, review, apply. The import stops and
   starts each server once; a node rebuilt minutes before can come back with
   half-pulled images (`exec format error`): rebuild it again.
3. **Before the control plane goes:** a `Backup` of each Postgres cluster and
   `pg_switch_wal()`, a copy of Zitadel's `iam-admin` and `iam-admin-pat`
   Secrets (only Zitadel's first start writes them), then shut the old node
   down and detach it from the network and its placement group.
4. **The new control plane** takes 10.10.1.10 and cp-1's name and is rebuilt
   with its config; `tofu state rm` the old one, import the new one, apply
   with `-replace=talos_machine_bootstrap.cluster
   -replace=talos_cluster_kubeconfig.cluster`, and `talosctl bootstrap` if
   etcd still waits. Reboot the workers: their kubelets register again and
   their `cni0` bridge drops the old cluster's pod range.
5. **Postgres** bootstraps from those backups and archives under the next
   serverName (the patch in `infrastructure/configs/test`). Push it, then step
   10 (Flux), and put the two Zitadel Secrets back.

`api_lb_location` and `ingress_lb_location` (fsn1 in `terraform.tfvars`) kept
both load balancers, so DNS, the kubeconfig and Lens didn't change.

## Keeping it current

Nothing to do: a develop push that changes what the images are built from (or
the chart) publishes a new build, and Flux upgrades the release within five
minutes of it; the migration Job runs first. Configuration changes reach the
cluster when they reach `develop`. To hold the cluster at one build, set
`WELDSUITE_IMAGE_TAG` in `clusters/test/cluster-settings.yaml` to its tag and
the HelmRelease's chart version (the `apps` patch in `clusters/test/layers.yaml`)
to its chart version. The marketing site follows its repository's `main` the
same way; to hold it, set the chart version in `flux/apps/marketing/marketing.yaml`.

`flux get helmreleases -A` shows the chart version each release runs;
`kubectl -n weldsuite get deploy weldsuite -o jsonpath='{..image}'` the image.

## Switching to develop

For the cluster built while it followed `deploy/eu-test` (on its images of
`0aeda04f9`, from before wave 3). Once this is in `develop`:

1. **Secrets the newer server reads.** The test cluster's
   `secrets/test/secrets.sops.yaml` predates them:
   - `weldsuite-env`: `WIDGET_TOKEN_SECRET`, `COLLAB_ROOMS_SECRET`,
     `INTERNAL_API_SECRET`, `WELDREACH_WARMUP_KEY` (64 hex characters),
     `LIVEKIT_API_KEY: weldsuite`, `LIVEKIT_API_SECRET` (48 hex characters);
   - a new `livekit-env` Secret in the `livekit` namespace:
     `LIVEKIT_KEYS: "weldsuite: <the LIVEKIT_API_SECRET above>"` and
     `REDIS_PASSWORD`, the value of `valkey-users`' `default`.

   `fill-secrets.mjs --update` adds exactly those (and whatever the examples
   gain later), with the age key from step 7. It decrypts in memory, keeps
   every value the file has, takes `REDIS_PASSWORD` from it, and prints names
   only:

   ```bash
   SOPS_AGE_KEY_FILE=~/weldsuite-eu-test.agekey \
     node rust/deploy/flux/scripts/fill-secrets.mjs --update rust/deploy/flux/secrets/test/secrets.sops.yaml
   ```

   Then commit the file through a pull request (`git diff` shows only
   `ENC[…]` values). The collab-rooms pods need `COLLAB_ROOMS_SECRET` to
   start, so this comes before the switch.
2. **Packages.** Make `weldsuite-collab-rooms` and `charts/weldsuite` public
   after the first develop build (step 8).
3. **Servers.** From the checkout that holds the local state, `tofu apply`
   with the merged module: it adds the `weldsuite-eu-test-livekit` firewall to
   worker-1 and worker-2 and should change nothing else (read the plan). Then
   label those two once, since OpenTofu doesn't push machine configs to
   running servers:
   `kubectl label node weldsuite-eu-test-worker-1 weldsuite-eu-test-worker-2 node.weldsuite.org/livekit=true`.
4. **DNS:** `livekit.test.weldsuite.eu` and `turn.test.weldsuite.eu` (step 6).
5. **Flux onto develop:**

   ```bash
   flux create source git flux-system \
     --url=https://github.com/weldsuite/weldsuite --branch=develop
   flux reconcile kustomization flux-system --with-source
   flux get kustomizations --watch
   ```

   The `sources` layer drops the old chart source; the `apps` layer upgrades
   the release to the newest develop chart, running the migrations of every
   commit since `0aeda04f9` first. Watch `flux get helmreleases -A` and the
   migration Job's log (`kubectl -n weldsuite logs job/…`).
6. The `deploy/eu-test` branch is no longer read by anything; delete it once
   the cluster runs from `develop`.

## Tearing it down

`tofu destroy` in `rust/deploy/hetzner`, then delete the buckets and the Talos
snapshot in the Hetzner console. The branch and the encrypted secrets can stay.
